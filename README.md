# トロロの街 (prototype)

街の管理人・工房の店主としてコザクラインコたちの暮らしを眺める箱庭シム。Expo SDK 54 (React Native) + TypeScript。Expo Go(SDK 54対応版)でそのまま実機確認できます。

プレイヤーは鳥を直接操作しません。中央の街と周囲のフィールド(敵・採掘資源・お宝)を、仲間になった鳥たちが各々の意思で歩き回ります。**素材・お金はまず鳥個人の所有物になり**、プレイヤーは街の管理人・商人として、鳥から素材を買い取ったり、依頼掲示板で欲しい素材を発注したりして、街の共有資源(倉庫)を少しずつ蓄えます。

## ゲームループ

0. **スタート時の鳥選択**: ゲームを初めて開始すると、ビビ・ハク・トロロ・モネの4羽から一緒に街を始める1羽を選ぶ選択画面が表示される(役割・性格が伝わる紹介文付き)。選んだ1羽だけが最初から街にいる状態でゲームが始まり、街の役場も「ボロ役場」(🛖)として表示される。残り3羽は`isRecruited: false`のまま、マップにもステータス画面にも表示されず、AI行動も一切しない——ただしそれぞれ専用の加入トリガーを常時チェックしており(`game/recruitment.ts`)、条件を満たすと自動的に仲間になり、その場で「🎉 新しい仲間!」の簡単な演出(アバター+一言セリフ)が表示される。1度でも1羽を選ぶと、以後は常に街の画面が表示される。
   - 🟡 ビビ: 街レベル到達(役場が「村役場」🏘️になる程度=街の発展ポイントが60pt。土地解放1回で30pt入るので、土地を2区画解放すればほぼ到達——`data/townGrid.ts`のgetTownLevel)。
   - 🩵 ハク: 専用クエスト「初めての採取に成功する」を達成(自由行動・依頼どちらの採取でも可。`useQuestStore`に一度だけ記録される)。
   - 🟢 トロロ: マップ探索中の偶然の出会い。フィールド上の特定地点(❓マーカーで示唆)に活動中の鳥が近づくと、低確率で毎ティック抽選される。
   - ✨ モネ: トロロと似た仕組みの別地点での偶然の出会い、またはオオカミ級の敵を初めて討伐すると即座に加入(どちらか早い方)。
1. **街とフィールド**: マップ中央に街、その周りに森・鉱山・キノコ畑・湖・遺跡といった自然な区画があり、それぞれのエリア専用の素材(森=木材/木の実/薬草/羽根、鉱山=鉱石/宝石/石炭、キノコ畑=キノコ、湖=魚/真珠/水草、遺跡=遺物/魔石/古いコイン)が手配置される、常設の1つのマップ(ステージ制ではない)。街の周囲には木や花の装飾も配置される。
2. **個体AI(性格は重み付け、絶対ではない)**: 仲間になった鳥はそれぞれ独立したAIで行動する(1つの群れとして固まらない)。戦闘・採掘・探索・休憩のどれも全員が行いうるが、性格によって選ばれやすさと危険地帯への忌避度が変わる。
   - 🟢 トロロ(vanguard): 戦闘・探索に大きく偏るが、採掘や休憩もする。危険は気にしない。
   - 💛 ビビ(clingy): 休憩・探索を好むが、戦闘や採掘もする。危険は苦手。
   - 🩵 ハク(cautious): 休憩に大きく偏るが、危険度の低い相手となら普通に戦う。
   - ✨ モネ(freeSpirit): 採掘・お宝回収に大きく偏るが(納品+20%)、資源が無ければ戦闘や探索もする。
   - 敵と遭遇した際の戦闘選択率は、その敵の強さ(攻撃力)と各鳥の危険忌避度に応じて下がる(弱い敵ならほぼ誰でも戦う)。
   - 複数の鳥が重なりそうになると、毎ティック軽く押し合ってすれ違う(`separateBirds`)。
   - 敵自身も自分の縄張り(スポーン地点周辺)をランダムに徘徊し、近くに鳥を見つけると追跡する。見失ったり離されすぎたりすると縄張りへ引き返す(`game/enemyAi.ts`)。追跡中の鳥が街エリアのゾーン境界(`getTownZoneRadius`)の内側に入った時点でも追跡を諦める——街を「安全地帯」として扱い、敵が街の中まで入り込んでくることはない(実機で敵が街エリアに侵入して見える不具合の修正)。
3. **気分**: エナジーの代わりに「普通/眠い/ご機嫌/お腹すいた/お金が欲しい」のいずれかの気分を持ち、時間で変化する。眠いと自分の家へ戻って休む。お腹がすくと街の「お店」へ行って基本食料を食べる。
4. **常に目的を持つ**: 優先順位は「弱った時の帰宅療養 > 依頼の遂行 > 持ち帰り中の荷物を家へ届ける > 空腹ならお店へ > 眠いなら帰宅 > (売る物があれば)お店で売却 > 性格による重み付き選択(戦う/採る/探検する/休む/遊ぶ) > 川や池で息抜き、または目的地のある散歩、または寄り道」。何もすることがなくなる状態は存在しない(遊ぶ・寄り道・雑談についてはフェーズ11参照)。HPが最大値の30%以下(またはHP0)になると、他の何よりも優先して自分の家へ戻り、全回復するまで療養を続ける(全回復するまでは他の行動に戻らないため、弱ったまま戦闘へ舞い戻ってすぐまた弱るループは起きない)。HP0になった瞬間は「疲れたから帰る〜!」のような軽い一言を吹き出しで見せてから帰宅する演出になっている。
5. **鳥ごとの経済**: 採取・討伐・お宝で得た素材やゴールドは、まず鳥自身の個人所有物になる(`BirdState.gold` / `BirdState.inventory`、`useBirdEconomyStore`で永続化)。鳥は気分(特に「お金が欲しい」)や在庫を見て、自律的に街のお店まで歩いて行き、一番多く持っている素材を(1回の取引につき上限あり)プレイヤーに売る。プレイヤーが買い取れる分だけ購入され(所持ゴールドが足りない時は買える分だけ購入)、鳥は代金を受け取る。素材の持ち物合計には上限(`BIRD_INVENTORY_CAP`、現状150個)があり、実機報告(特定の素材を1000個近く持ち続け、行動効率に影響している様子)を受けて追加した——上限に達すると、普段は確率判定(`SELL_CHECK_CHANCE_BASE`/気分が「お金が欲しい」ならより高確率)で決めている売却トリップを、その場で必ず実行するようになる(`game/ai.ts`)。この「上限に達した時の売却」は、1回の取引の上限(個数・ゴールドとも)を通常の少額トリップ用の値(`SELL_MAX_PER_TRIP`=8個、`SELL_MAX_GOLD_PER_TRIP`=15G)のまま流用していたため、安い素材(木材4Gなど)では1トリップにつき1〜3個しか売れず、150個の上限を到底解消できずに毎ティック強制売却トリップが再発生し続け、「売る」行動だけがずっと続いて他の行動(採取・討伐・依頼対応)が一切行われなくなる実機報告(バグ)につながった。上限超過時専用のより大きな上限(`OVERFLOW_SELL_MAX_PER_TRIP`=60個、`OVERFLOW_SELL_MAX_GOLD_PER_TRIP`=300G、`OVERFLOW_SELL_MARGIN`=20個)を設け、通常のちょっとずつの取引ペース(プレイヤーの資金を守るための`SELL_MAX_GOLD_PER_TRIP`など)とは別枠にすることで、上限超過はごく数回のトリップで解消し、他の行動とバランスよく交代するよう修正した。ただしこの強制トリップには、プレイヤーが実際にその素材を買い取れるかどうかの判定が入っていなかったため、街の資金が乏しい状況(かつ、強制トリップに専有されている間は他の行動で稼ぐこともできない)だと、鳥が売却トリップを毎ティック強制されては0個で終わる、を無限に繰り返す実機報告があった——`AiWorld.playerGold`を追加し、上限超過による強制発動は「プレイヤーが最低1個分の代金を今払えるか」を確認できた時だけに限定し、払えない間は通常の低確率ロールにフォールバックして鳥が他の行動(討伐・依頼対応など、街の収入源になる行動)に戻れるようにした。それでもなお「街の資金が尽きるまで売り続け、少しでも増えるとまた売りつけてくる」実機報告があり、根本的に「上限を超えて溜め込ませてから慌てて売らせる」設計自体が、プレイヤー自身の限られた資金を奪い合う構造になっていたと判断した——最終的に、`BIRD_INVENTORY_CAP`を「超えたら急いで売る」閾値から「そもそも超えられない」物理的な上限に変更した(`game/inventoryCap.ts`のaddCappedInventory。採取の持ち帰り・採掘ボーナス・討伐ドロップ・オフライン追いつき計算など、素材が鳥の持ち物に加算されるすべての箇所で、上限に達している分は加算されず捨てられる=そもそも入りきらない)。これにより上限超過そのものが二度と起こらなくなり、上限に達した際の売却も「わずかな余剰(`OVERFLOW_SELL_MARGIN`=20個程度)を売るだけ」で済むようになった。またこの変更に合わせて、既存セーブが持っていた上限超過分(実機報告の1500個など)は次回起動時に上限までその場で切り捨てる一括補正を`useBirdEconomyStore`のgetWalletに追加し、既にできてしまっていた大量の在庫を、これ以上の売買を経ずに即座に解消した。
6. **依頼掲示板**: 掲示板に同時に出せる依頼は最大3件(`MAX_ACTIVE_REQUESTS`)まで。プレイヤーはプリセット(`data/jobPresets.ts`のJOB_PRESETS)から依頼を選んで出す(満員の時は投稿不可、掲示板側にも「満員」表示が出る)。手が空いている鳥が、自分の性格・気分・報酬額から判断して受けるかどうかを決める(命令ではなく募集。受けてもらえないこともある)。達成すると報酬(ゴールド+経験値+街の発展ポイント+街評価)が対応した鳥・街にそれぞれ加算され、その枠は単に空く——以前はランダムなプリセットから新しい依頼が自動的に補充されていたが、これだと掲示板が常にランダムな依頼で埋まってしまい、プレイヤーが本当に出したい依頼を出せなくなる(実機報告)ため廃止した。依頼掲示板には対応者名と進捗(◯/◯)が表示される。依頼には4種類あり(`JobRequest.kind`)、それぞれ達成の仕方が異なる。採集・討伐の2種は、鳥が受注時・納品時にそれぞれ役場へ実際に足を運ぶ3段階の行動になっている(`BirdState.jobStage`: `toAccept`→役場へ受注に向かう、`working`→採集・討伐そのもの、`toDeliver`→役場へ納品に向かう。役場に着いた瞬間に初めて報酬・経験値が加算される)——実機フィードバックを受けて、受注・達成が一瞬のフラグ切り替えではなく実際のお使いとして表現されるようにした。採集依頼は、鳥がその場で必要素材を十分な数持っていれば(実機フィードバック:「鳥の在庫からも出せるようにしてほしい」)採取ポイントへ行かずにその場で納品分を確保でき、不足分だけ採取ポイントへ向かう。納品に向かっている間、掲示板には「(鳥の名前)が役場へ納品に向かっている」と表示される。
   - **採取**(`gather`): 指定した素材を指定数集める。受けた鳥が該当する資源を優先して自分で集めに行き、必要数に達するまで(1回で届かなければ何度でも)集め続ける。達成すると素材は直接プレイヤーの倉庫に入る(既存の唯一の依頼種別)。
   - **討伐**(`hunt`): 指定した種類の敵(スライム/コウモリ/オオカミ、名前が同じ個体はマップ上の複数体すべて対象)を指定数討伐する。受けた鳥はその種類の敵を優先して探して戦いに行き、実際に討伐に関わった回数が必要数に達すると達成(他の依頼と違い、進捗判定は毎ティックの戦闘解決後にまとめて行われる)。
   - **クラフト**(`craft`): 指定したアイテムを指定数、加工パネル(🛠️)で加工する。鳥の自律行動ではなくプレイヤー自身の加工操作がそのままカウントされる(受けている鳥は特に何もせず、通常通り自由に行動する——加工はプレイヤーの手作業であって鳥の仕事ではないため)。
   - **商人への納品**(`merchantDeliver`): 指定したアイテムを指定数、来訪中の商人に納品する。商人が来ていない間は進捗できず、掲示板に「商人の来訪を待っています…」と表示される。商人が来ている間、プレイヤーの倉庫に十分な在庫があれば「📦 納品する」ボタンで納品できる(在庫が足りない分は後から追加で納品可能)。
7. **戦闘・採掘・お宝**: 敵との戦闘・資源の採掘・お宝の開封は鳥が現地に到着すると自動で行われる(タップ操作は不要)。HPが最大値の30%以下(HP0を含む)になった鳥はその場で足踏みするのではなく自分の家まで戻り、全回復するまで療養する(消滅はない。全回復するまでは戦闘へ戻らない)。討伐報酬は、貢献したダメージ量に比例して関わった鳥たちに分配され、その一部(既定40%)が「治安協力金」としてプレイヤーの収入になる。お宝のゴールドは発見した鳥がそのまま受け取る。敵の頭上には⭐の数(1〜3個)でおおまかな強さの目安を常時表示する(`getEnemyStrengthTier`。HPと攻撃力から算出した相対的な強弱で、正確な数値までは出さない——実機フィードバックを受けて追加)。
7.5. **モンスタードロップ**: 敵を倒すと、種類ごとに設定された確率テーブルに応じて素材やアイテム(武器・防具・レア)がドロップし、参加した鳥の中からランダムに1羽がそれを手に入れる(鳥個人の持ち物になり、ステータスカードで確認できる)。
8. **持ち帰り**: 自由行動で採掘した素材は、その場で即座に手に入るのではなく、鳥が自分の家まで運んで帰ってから自分の所持品に加算される。運んでいる間は鳥の頭上に素材アイコンが表示される(依頼で集める素材は従来通り依頼達成時にプレイヤーへ直接加算)。採掘ポイント1箇所あたりの採取量(`data/world.ts`のMINING_NODE_DEFSのamount)は、以前の値だと採取特化の鳥が10分少々で持ち物上限(150個)に達してしまう実機報告(オフライン進行では31分で986個という報告も)を受けて約4割に調整済み——採取に励んでから数十分でようやく上限に近づく程度のペースを目安にしている。
9. **リスポーン**: 倒した敵・採り切った資源・開けたお宝は一定時間後に元通り復活する(`src/game/config.ts`の`ENEMY_RESPAWN_MS`等で調整可)。世界が枯渇して止まることはない。
10. **見た目**: 淡いパステルカラー(空色・クリーム色・若草色)の可愛い放置ゲーム風の配色。カードやボタンには柔らかいドロップシャドウを、要所にピンクのアクセントを使用。4羽は公式イラストを加工した2頭身の本体スプライト(`assets/birds/{id}/base.png`、256×256・完全透過・共通アンカー)でマップ・ステータスカードに表示される。
11. **街の開拓**: 街の中心(町役場)を囲む土地があり、東西南北の内側4区画は最初から使える。内側2リング(24区画)はゴールド+素材で解放できる(遠い区画ほど高コスト)。さらに外周1リング(24区画、合計48区画)は、街レベルが3(町役場)に到達するまで解放を試みることすらできない——街の発展段階が進むほど、街エリア自体が実際に広がっていく。ロック中の区画をタップすると、解放に必要な「ゴールド」「素材の種類・数量」を現在の所持数と見比べられるモーダル(`PlotUnlockModal`)が開き、条件を満たしていれば「解放する」ボタンでその場で解放できる。解放済みで何も建っていない区画をタップすると建設メニュー(`ConstructionModal`)が開き、`data/buildingOptions.ts`のカタログ(道具屋の出張所・餌屋の出張所・武器屋・防具屋・花壇・公園・水浴び場の7種)からゴールド+素材を払って選んで建てられる(建てた出張所・武器屋・防具屋をタップすると、既存店舗と在庫を共有する店舗モーダルが開く。花壇・公園・水浴び場は売買機能を持たない。公園・水浴び場は鳥が「遊ぶ」行動の目的地になる——フェーズ11参照)。建設できるかどうかは、区画が解放済みかどうか(外周1リングはさらに街レベル条件も)だけで決まり、街エリアのゾーン楕円(次項参照)は一切関係ない——過去に一度、ゾーンの内側にある区画でしか建設メニューが開かないよう制限したことがあったが(実機フィードバック「街を街として固めたい」への対応)、その後の検証でゾーン楕円は既存の敵・採掘ポイントと重ならないよう意図的に小さく保たれており、区画48個中40個(リング2・3)には街レベルをいくら上げても永久に届かないことが判明し、「街が発展してゾーンが広がれば建てられる」という案内自体が嘘になってしまっていた。ゾーンを区画グリッド全体を覆うサイズまで拡張する案も検証したが、そうすると今度は森・鉱山などの手配置コンテンツの大半(敵5体・採掘ポイント10箇所・川辺1箇所)を丸ごと呑み込んでしまい、かつ一部の敵をゾーンの外へ押し出そうとするとマップ座標の範囲(0〜1)からはみ出してしまうことも判明したため断念。最終的に、ゾーン楕円は「街の管理人の生活圏」を示す純粋な演出に戻し、建設可否の判定からは完全に外した。南北の区画には最初から実際に機能する「お店」が2つ建っている——南が🛠️道具屋(帽子・盾)、北が🌾餌屋(餌)。武器屋・防具屋はこの2つに含まれず、街のどこかに建設するまでは存在すらしない(次項参照)。どちらもタップするとまず店名・ジャンルのメニューが開き、「🛠️加工する」(その店のジャンルのレシピだけで加工)・「📦商品を並べる」(街の倉庫にある加工品をその店の棚に並べる)・「👀在庫を見る」(現在棚に並んでいる商品を見る)の3つから選べる。プレイヤーの主な行動サイクルは「鳥が素材を集める→プレイヤーが加工する→店へ商品を並べる→鳥が(または旅人が)購入する→売上が入る」。この2つの常設店舗は、街エリアのゾーン境界(次項参照)に対して十分な余白を持つ専用の座標(`townGrid.ts`のSHOP_AXIS_OFFSET)に固定配置されており、街レベルが上がって境界が広がっても常に内側に収まる。
11.5. **餌屋の仕入れ**: 餌屋のシード・粟穂・木の実・野菜は、加工品とは別枠で、NPC業者が街の資金を使って自動的に棚を補充する通常商品(街にコストが発生する仕入れ)。一方、既存の「初期の安価な餌(原価0で無料生成、街の資金は一切使わない)」は今回のアップデートでも仕様そのまま——鳥が空腹になると餌屋へ行き、棚に買える餌があればそれを購入(街の収入になる)、なければ従来通り無料の基本食で空腹を満たす(空腹は必ず解消される)。栄養ビスケット・高級ブレンド・元気ペレット・幸運のおやつは、加工で作れる高級餌(将来的な効果付与を見据えたデータ構造を用意済みだが、現状は効果未適用)。
11.6. **鳥の装備調達**: 鳥は自分の武器・防具・帽子・盾のいずれかが空いている時、時々そのカテゴリを扱う店の棚を確認し、買えるものがあれば自分のお金で購入する(1カテゴリにつき1つで十分と判断し、無限に買い続けたりはしない)。購入額は街の収入になる。帽子・盾は常設の道具屋で確認できるが、武器・防具は対応する店(武器屋・防具屋)が街のどこかに建設されるまでは確認自体が行われない——建設された場所は`data/townGrid.ts`のgetAllShopPositionsが街の区画を検索して見つけるので、どの区画に建てても鳥はちゃんと辿り着ける。

11.7. **役場の発展段階**: 街の発展ポイント(`useTownStore.developmentPoints`。土地解放1回につき30pt、建設1回につき20pt、依頼達成でも加算)が一定値に達するたび、役場は5段階で発展する——① ボロ役場🛖(0pt) → ② 村役場🏘️(60pt) → ③ 町役場🏛️(180pt) → ④ 自然保護局🌲(400pt) → ⑤ トロロ自然保護本部🏯(800pt)。段階が上がるたびに「🎊街が発展した!」のお祝いモーダルが表示され(「発展ポイントが◯◯に到達しました」と条件も明記)、マップ上の役場の絵文字・名前表示も切り替わる。役場自体をタップすると`TownStatusModal`が開き、現在の発展ポイントと次の段階までの残りポイントをいつでも確認できる。「地図上の色付きエリアは街の雰囲気を示す演出です。建物は解放済みの土地ならどこでも建てられます」という一文も添えてあり、街エリアのゾーン楕円(演出)と建設可否(解放状況+街レベルのみで決まる)が無関係であることを明示している。発展ポイントとは別に「街評価」(`reputation`)という人気度・知名度の指標も依頼達成のたびに独立して蓄積されるが、現状は数値を貯めるのみで実際の影響先(博物館・商人来訪頻度など)は未実装。

11.8. **街エリアと冒険フィールドのゾーン分け**: マップは「街エリア」(役場・建物・お店が集まる、くつろぎ・買い物の場)と「冒険フィールド」(採取ポイント・敵が点在する、活動の場)にはっきり分かれている。街エリアは役場を中心にした暖色の楕円形の背景と、🪵の柵ポストを楕円境界に沿って20本並べた輪(主な境界表現)+その内側の点線リング(副次的な補助線)で視覚的に区切られる(`data/townGrid.ts`のgetTownZoneRadius/TOWN_ZONE_RADIUS)。以前はこの楕円が街レベルごとに少しずつ大きくなる仕様だったが、レベルごとに「既存の敵・採掘ポイントと重ならないか」を再検証し続ける必要があり(このゾーン境界は実際に複数回の実機不具合の原因になっていた)、固定サイズに変更——街の発展の実感は、楕円そのものではなく道網の広がりや新しい建物の出現で表現するようにした。柵ポストの本数・開始角度は、常時存在する区画(南北の店・東西の解放済み区画)・商人待機スポット・4軒の家のいずれにも柵が重ならないよう数値探索で決めてある(リング1の斜め区画だけは仕様上もともと柵のすぐ外側に位置する)。区画グリッドが実際に使う7本の行・7本の列すべてに沿って道の帯を敷いており(`roadGridNodes`。以前は役場を通る十字1本だけだった)、区画同士が「道で区切られた街区」として視覚的にまとまるようにしてある。鳥の「お腹すいた」「休憩したい」といった街エリア向けの用事(自由行動時の「探検」「休憩」)は街エリアの楕円の内側だけに、「採取したい」「討伐したい」は外側の冒険フィールド側だけに、それぞれの徘徊範囲が動的に収まるようになっている(`game/ai.ts`のrandomPointInField/randomPointNearTown)。冒険フィールド側も、森・鉱山・キノコ畑・湖・遺跡それぞれのエリアに、手描き風の地面タイル素材(`assets/tiles/`、`data/tileImages.ts`)を低透明度(0.32)で敷き詰めた背景パッチを敷いて緩やかなゾーニングを示している(森=濃い緑+小花、鉱山=岩混じりの草地、キノコ畑=クローバー、湖=青い小花、遺跡=土面)。各パッチは同系統のタイルを2種類ランダムに(ただし`WorldMap`の再描画のたびに変わらないよう、セル位置から決定的に計算した疑似乱数で)混ぜて敷いており、同じタイルが規則的に並ぶ格子模様に見えないようにしている。パッチの中央には「⛏️ 鉱山」のような小さなラベルを重ねて、何のゾーンかひと目でわかるようにした。街エリアの背景にも同系統の草地タイルをうっすら重ねている。タイルは水彩調で鳥キャラクターとは絵柄がやや異なるため、あくまで背景の低透明度テクスチャに留め、主張しすぎないよう調整してある。採掘ポイントなどの既存アイコンには軽いテキストシャドウを入れ、タイル背景の上に浮いて見えすぎないよう馴染ませている。街エリアの楕円は、既存の敵・採掘ポイントの配置と重ならないよう意図的に控えめなサイズに抑えてあるため(街の管理人の生活圏という「街の核」を示す表現であり、区画グリッドの外周を隙間なく覆う保証ではない)、遠方の土地区画の対角線上の角が楕円の外にはみ出すことがあるが、これは仕様。ロック中の未解放区画のうち、街レベルの条件をまだ満たしていないものは、金額表示の代わりに「Lv.◯」の必要レベルバッジと、通常より暗く落とした地面タイル背景(「未開拓」感の演出)で表示され、まだ購入を検討する段階にないことが一目で分かる(解放済みだが未着手の区画も同じ地面タイルを使い、殺風景さを解消している)。採掘ポイントの周りには土のくぼみタイルを1枚アクセントとして重ね、掘り跡らしさを添えている。街レベル3(町役場)に到達すると、街エリア(区画外周1リング)・冒険フィールド(奥地の鉱脈+強化されたオオカミの縄張り)の両方が同時に解放され、発展の実感と街レベルの意味づけが結びつくようにしてある。

11.9. **マップのパン・ズーム**: 区画総数が48に倍増したため、マップは画面サイズに合わせて縮小表示するのではなく、固定の「実サイズ」(`WorldMap`のWORLD_CANVAS_WIDTH/HEIGHT、900×1400)で描画される。指でドラッグして自由に移動でき、2本指のピンチで拡大・縮小できる(`components/PannableMap.tsx`、iOS標準のUIScrollViewズーム機能を利用。新規ライブラリの追加なし)。最小ズーム倍率は画面サイズから動的に計算され、街全体を見渡せる程度に自動調整される。アプリ起動時・街画面を開いた時は、常に役場が画面中央に来るように自動でスクロールされる(拡張された外周区画・奥地のフィールドはスクロールして初めて見える)。ミニマップや特定要素へのジャンプ機能は今回未対応。

(開発中、実機でマップ上のタップ・ドラッグが起動直後から一切反応しない不具合が発生し、一時的にこのズーム機能を疑って撤去したことがあったが、実際の原因は無関係な別バグ(次項参照)だったと判明したため、ズーム機能はそのまま復元済み。)
12. **鳥の家**: 4羽それぞれに専用の家が街の外周に1軒ずつあり、色で見分けられる。眠い気分になると、また採取した荷物を届けにも、自分の家に帰るようになった。家をタップすると`HouseInventoryModal`が開き、その鳥専用の収納が見られる(実機フィードバックを受けて追加)。①**装備品のストック**: 予備の武器・防具・帽子・盾(`items`のうち装備中でない分)を一覧表示するだけの閲覧専用セクション——持ち物に上限がなく管理の必要がないため。②**ご飯のストック**(`BirdState.houseFood`、上限`HOUSE_FOOD_CAP`=5個): 街の倉庫にある食料アイテムをこの家に「しまう」/「戻す」でき、鳥が空腹になった際はまずこの備蓄を(店へ移動せず即座に)消費してから、なければ従来通り餌屋へ向かう(`game/ai.ts`のtryEatHouseFood)。③**お気に入りのお宝**(`BirdState.houseTreasureIds`、上限`HOUSE_TREASURE_CAP`=5個): 換金アイテムを`items`から物理的にこのリストへ移すことで、鳥の自律的な商人への売却判定(`hasConvertibleItems`/`pickMerchantSellOffer`は`items`しか見ない)から確実に除外される——フラグを立てるのではなく実際に別の入れ物へ移動させる設計なので、除外漏れが起きない。
13. **街の管理人**: プレイヤーの分身として、町役場のそばに常駐するキャラクターがのんびり佇んでいる(操作はできない)。
14. **街の収益**: プレイヤーの収入源は — 討伐の治安協力金(討伐報酬の40%。クラフト素材・戦闘報酬のみが対象で、換金アイテムには一切適用されない)、鳥が街で基本食料を買う際の購入額(生成自体は常に無料でプレイヤーの資金は使わない)、時々街を訪れる「旅人」が倉庫の素材をランダムに買っていく分、鳥が餌屋・道具屋で実際に商品を購入した売上、そして鳥が商人に換金アイテムを売った際の折半分。それぞれ`PlayerState`の`tollFromHunt`/`tollFromFood`/`tollFromTraveler`/`tollFromShop`/`tollFromMerchant`に累計として記録される(実際に使える残高は`gold`で、これらは将来の帳簿UI向けの内訳)。唯一の経常的な支出は餌屋の商品仕入れ(`expenseFeedRestock`)で、仕入れ値より高く売れる分だけ純利益になる。鳥が売りに来る1回の取引でプレイヤーが支払える金額には上限(`SELL_MAX_GOLD_PER_TRIP`)があり、治安協力金などの収入が単発の売買で食いつぶされて残高が伸び悩まないようにしてある。旅人の来訪チェック頻度(`TRAVELER_CHECK_CHANCE`)は、以前は商人の来訪チェックの約7倍・鳥が街に素材を売る頻度をも上回る値になっており、実機で11時間オフラインにした際に街の素材倉庫が完全にゼロになる不具合の原因になっていた——商人と同程度の頻度まで引き下げ、旅人はあくまで「たまに立ち寄る」flavor程度の存在に留めた。
15. **経験値とレベルアップ**: 討伐に参加した(ダメージを与えた)鳥は敵の種類に応じた経験値を得る(雑魚5〜7exp、やや強い敵ほど多い。分配ではなく参加者全員が満額)。一定量たまるとレベルアップし、攻撃力・HP・防御力・素早さが少し上がる。レベルアップは生活ログにも記録される。以前は攻撃力・HPの上昇分が`BirdWallet`に永続化されておらず、アプリを再起動するたびキャラクター素の初期値まで戻ってしまっていた(防御力・素早さだけは永続化されていたため、レベルが高いのに攻撃力・HPだけ低いままに見える実機報告の原因)——`BirdWallet`に`atk`/`maxHp`を追加し、他の2ステータス同様に永続化するよう修正。修正前からの既存セーブも、記録済みのレベルに応じた分だけ攻撃力・HPを遡って補正して引き継がれる(`useBirdEconomyStore`のgetWalletが担う)。ただし`useGameTimeStore`のオフライン追いつき計算(catchUpOffline)だけはこの補正を経ない生の`wallets`を直接読んでいたため、その1回だけ`undefined + 上昇量`が計算されて攻撃力・HPが`NaN`のまま永続化されてしまう不具合が上記の修正直後に発生した(実機報告)。catchUpOfflineもgetWallet経由(getAllWallets)で読むよう修正し、既にNaNになってしまったセーブも次回起動時に自動で復旧するようにした——のはずが、`JSON.stringify(NaN)`は`null`にシリアライズされる(NaNのままではない)ため、AsyncStorageに一度書き込まれたNaNは次回読み込み時には`null`として復元され、`Number.isNaN`チェックをすり抜けてしまっていた。`null + 上昇量`はJSでは0扱いで計算されてしまうため、レベル相応の値ではなく「0からわずかに上昇しただけ」の極端に低い攻撃力・HPになる(実機報告: 攻撃力・HPが激弱に)というさらなる副作用を生んでいた。`Number.isFinite`によるチェックに変更し、undefined/null/NaN/Infinityのいずれも一括して補正対象にするよう修正した——それでもなお1羽だけ、レベル86でHP15/攻撃力6という、キャラクター自身のレベル1初期値(HP70/攻撃力10)より低い値のまま治らない実機報告があった。これは一連の中間的な壊れ方のどこかで、Number.isFiniteでは検知できない「有限だが不合理に低い」値が一度persisted状態に書き込まれてしまったケースと考えられる。atk/maxHpはgrantExpの`+=`でしか増えないため、defense/speedと全く同じ回数だけ増えているはずで、「自身のレベル1初期値を下回っている」こと自体が、原因を特定できずとも壊れている確実な証拠になる——この不変条件(自身のbase値を下回っていたら補正)もチェックに追加し、原因の詳細を特定できていなくても今後同種の破損が起きれば毎回自己修復されるようにした。
15.5. **鳥ごとの基礎ステータス**: HP・攻撃力・防御力・素早さ・運の5つを個体ごとに保持(キャラクターごとに初期値が異なる)。素早さ・運は将来の移動速度差・ドロップ運への拡張を見込んで用意済みだが、現状は表示のみで挙動には未反映。満腹度・ご機嫌度も数値(0〜100)で保持し、既存の気分テキスト(「お腹すいた」等)と連動する — 満腹度は毎ティック減っていき、閾値を下回ると自動的に「お腹すいた」になる(ランダム抽選ではなく実際の空腹に基づく)。食事すると満腹度は全回復する。ご機嫌度はご機嫌/空腹の状態に応じて緩やかに増減する。
15.6. **装備**: 武器・防具・帽子・盾の4スロットを鳥ごとに持つ。帽子・盾は常設の道具屋で、武器・防具はそれぞれ専用に建設した武器屋・防具屋で買う(またはモンスターから武器・防具をドロップで入手する)と、対応するスロットが空いていれば自動的に装備される(上書きはしない。同じ種類の2つ目は持ち物として温存)。装備には攻撃力・防御力のボーナスがあり、実際の戦闘ダメージ・被ダメージ軽減に反映される。見た目の変化は今回は実装せず、`ItemDef.spriteVariant`という未使用フィールドだけ用意してある(将来、装備で見た目が変わる拡張をしやすくするため)。装備品(武器・防具・帽子・盾)の同一アイテムIDごとの予備在庫には上限(`EQUIPMENT_SPARE_CAP`=2、「装備中+予備1個」)がある——購入は既にスロットが埋まっているカテゴリを買い直さない仕組みになっていたため安全だったが、討伐ドロップの受け取り側には上限が一切なく、実機報告で同じ武器の予備が193個も積み上がっていた。`game/inventoryCap.ts`の`addItemCapped`を装備ドロップ・購入・採掘ボーナスドロップの受け取り全箇所に適用し、上限を超える分はフェーズ10の素材と同様その場で捨てずに換金する(店の販売価格の40%=`EQUIPMENT_SALVAGE_FRACTION`、街への還元はなく鳥個人のゴールドに直接加算——通常の売買と違い「重複品を鳥自身が処分した」という位置付けのため)。既存セーブが既に抱えていた上限超過分も、次回起動時に上限まで一括で換金・切り捨てる補正を`useBirdEconomyStore`に追加した。
15.7. **換金アイテムと商人**: 宝石・金塊・王家の宝飾品などの「換金専用アイテム」(`ItemDef.itemType: 'convertible'`)は、加工には使えず街の倉庫にも入らない、鳥個人が持つだけの純粋な資産。討伐・採掘の低確率ドロップでのみ入手できる(討伐報酬の治安協力金は一切適用されない)。街には時々(数分〜十数分に一度)「商人」が現れ、数分間だけ簡易的な店を構える。商人が滞在している間、鳥は自分の判断で ①持っている換金アイテムを商人に売る(代金は鳥50%/街50%で折半——「市場利用料」という名目で`tollFromMerchant`に計上)、②商人がその来訪ごとにランダムに用意した棚(通常アイテム中心・低確率でレア品)から欲しい物を自分のお金で買う(この代金は街の収入にはならない)、の両方を行いうる。プレイヤー側は🏕️アイコンをタップすると、残り時間と棚の中身を確認できる(閲覧のみ・取引は基本的に鳥に任せる)。唯一の例外が「倉庫の素材を売る」欄で、街の倉庫(`PlayerState.materials`)にある素材はどの鳥の持ち物でもなくプレイヤー(街)自身のものなので、旅人のランダム購入や鳥の自律売買を待たずに、商人の来訪中ならいつでもプレイヤーの意思でその場で売却できる(`sellMaterialToMerchant`。他の素材売却と同じ単価=`MATERIAL_SELL_PRICE`)。売却個数は+/-ボタン(10個刻み)で選んで指定できるほか、「全部売る」ボタンでまとめて売ることもできる——以前は在庫を丸ごと一括売却する仕様だったが、必要な素材までうっかり全部売ってしまう実機報告を受けて個数指定に変更した。旅人(街の在庫を一過性で消費し代金が街の収入になる)とは役割が完全に分離しており、`WorldState.merchant`として別データで管理される。
16. **生活ログ**: 画面下部に、採集・討伐(誰が倒して報酬がどう分配されたか)・売却・購入・依頼達成・旅人の来訪・レベルアップなど、直近10件の出来事が「誰が・何をして・どうなったか」が分かる一文で常時表示される。
17. **鳥ごとのステータスカード**: 🐦ボタン(または鳥をタップ)で、4羽それぞれの名前・レベル・経験値・所持ゴールド・持ち物・数値ステータス(HP/攻撃力/防御力/素早さ/運、装備ボーナス込み)・満腹度/ご機嫌度・現在の装備4スロット・現在の状態(採集中/討伐中/売却中/購入中/休憩中など)・現在の目的が見られるカード一覧を開ける。
18. **ステータス表示**: 画面上部には所持ゴールドと、鳥のようす(🐦)・加工(🛠️)・倉庫(🎒)を開くボタンのみを常時表示(全素材の常時表示はしない)。プレイヤーの所持品は倉庫画面で、鳥の所持品(素材+モンスタードロップのアイテム)はステータスカードで確認する。
19. **加工(プレイヤーの主な行動)**: 🛠️ボタンから、街の倉庫にある素材を消費してアイテム(武器・防具・レアの3種)を1つずつ作れる。必要素材が足りないレシピはボタンが押せない。加工品は街の倉庫(`PlayerState.items`)に貯まり、お店の品揃えに反映される。全レシピのうち最初から使えるのは3個(レザーハット・木の盾・栄養ビスケット)のみ(`CraftingRecipe.unlockedByDefault`)で、残りは加工パネルにそもそも表示されない。未解放レシピは次の4ルートのいずれかで入手でき、入手済みかどうかは`useRecipeStore`(永続化)が管理する: ①商人が滞在中にランダムで1つ「レシピの提供」として提示し、ゴールドを払って購入(`MerchantModal`の📜欄、購入は`buyMerchantRecipe`)、②鳥が採取を完了するたびに低確率でお土産として発見(`RECIPE_GIFT_CHANCE`)、③依頼掲示板の依頼(討伐・クラフトなど)を達成した時の低確率報酬(`RECIPE_QUEST_CHANCE`)、④モンスターを倒した時の低確率報酬(`RECIPE_COMBAT_CHANCE`)。いずれの場合も新規レシピを1つ得るたびに`RecipeUnlockModal`(「📜新しいレシピを手に入れた!」)が表示される。`usePlayerStore.craftItem`は未解放レシピでの加工をデータ層でも拒否する(UIボタンを隠すだけでなく)。
20. **永続化**: プレイヤーの所持ゴールド・素材(14種)・加工品・収入内訳、街の土地の解放状況・建物、そして各鳥の個人ゴールド・所持素材・持ち物(ドロップ品)・レベル・経験値は端末に保存(AsyncStorage)。フィールド上の鳥の位置・気分・依頼・生活ログは現状セッション内のみ(今後の課題)。
21. **ゲーム内時間とオフライン進行**: アプリを開いている間、ゲーム内カレンダー(`gameTimeMs`)は現実より60倍速で進む(現実1分≒ゲーム内1時間、`ONLINE_TIME_SCALE`)。ただし現状はティックベースの各種処理(リスポーン・商人の滞在時間など)はこの数値に連動しておらず、あくまで将来のシステム(街レベル・クエスト期限など)向けの土台。アプリを閉じていた間は、次回起動時に前回終了時刻からの経過時間をまとめて計算し反映する(最大8時間分でキャップ、それ以上閉じていてもキャップ分しか進行しない)。この「追いつき計算」は1ティックずつ再現するのではなく、性格ごとに実測した「1討伐/1採取にかかる平均ティック数」を使った概算(`OFFLINE_TICKS_PER_KILL`/`OFFLINE_TICKS_PER_GATHER`、`game/offlineProgress.ts`)で、実際に起動し続けた場合と釣り合うよう調整済み(討伐報酬の治安協力金・旅人の来訪に加えて、鳥が集めた素材を街のお店に売る自律売買もオンライン同様の頻度で概算再現し、代金分プレイヤーの所持ゴールドを減らして街の倉庫に素材を加算する。餌屋の仕入れ・商人の来訪・依頼はオフライン中は簡略化のため考慮しない)。この自律売買の概算は、通常の少額取引ペース(`SELL_CHECK_CHANCE_BASE`相当の頻度・`SELL_MAX_PER_TRIP`/`SELL_MAX_GOLD_PER_TRIP`の上限)だけで固定回数分計算しており、鳥の持ち物上限(`BIRD_INVENTORY_CAP`)を一切考慮していなかったため、最大8時間という長いオフライン時間だと採取ペースが売却ペースを大きく上回り、復帰時に特定の素材を1000個以上溜め込んだ状態になる実機報告があった——追いつき計算の最後に、持ち物上限を超えている間は上限超過時専用のより大きな上限(`OVERFLOW_SELL_MAX_PER_TRIP`/`OVERFLOW_SELL_MAX_GOLD_PER_TRIP`)で追加の売却を繰り返す処理を加え、オフラインで溜まりすぎた在庫がそのまま持ち帰られないようにした。集めた素材のうちどれだけが実際に街の倉庫入りしたか(自律売買で売れた分。旅人がその後買っていく分と相殺されることもある)は「おかえりレポート」モーダルに内訳として表示される。起動時には計算結果を「おかえりレポート」モーダルで表示する(経過時間・街の収入内訳・鳥ごとの獲得ゴールド/素材/レベルアップ・一言ハイライト)。
22. **公園・水浴び場と鳥の行動拡張、ひらめきシステム(フェーズ11)**: 採取・討伐・休憩・買い物中心だった鳥の行動に、寄り道・雑談・遊ぶの3つを追加し、そこから偶発的な成長(ひらめき)が生まれるようにした。
    - **公園・水浴び場**: `data/buildingOptions.ts`に売買機能を持たない建物として追加(絵文字は🌳/🛁の既存流用、新規画像なし)。建設済みの区画は`data/townGrid.ts`のgetAllAmenityPositionsで検出され、鳥は自由行動の重み付き選択の5つ目の枠(`ActivityCategory: 'play'`)として、性格ごとの重みに応じてここへ向かう(建物が1つも無い間はこの枠の重みは常に0)。
    - **遊ぶ**: 公園・水浴び場に到着すると`activity: 'playing'`になり(頭上に🎉)、生活ログにも「(鳥の名前)が公園で遊んでいる」のように表示される。一定ティック滞在したら通常の行動選択に戻る。
    - **寄り道**: 次の行動を新しく選び直すタイミング(既存の行動を継続中の割り込みではない)で、低確率(`DETOUR_CHANCE_BASE`)で「寄り道」(`activity: 'strolling'`、頭上に💭)を挟む。ジョブ・戦闘・採掘の状態機械には一切触れない設計にしてあるため、これらの進行中の処理が寄り道に割り込まれることはない。当初はランダムな近くの1点へ歩いて行く実装だったが、その距離が1ティックの移動量に収まってしまい実質瞬間移動のように見えて何が起きているか分からないという実機フィードバックがあり、`DETOUR_DWELL_TICKS`(3秒)その場に立ち止まるだけの演出に変更した(次項も参照)。
    - **雑談**: 毎ティック、仲間になっている2羽が近く(`CHAT_PROXIMITY_DIST`)にいて、かつどちらも「手が空いている」状態(採集・討伐・依頼・運搬中などではない)の時、低確率(`CHAT_CHANCE_BASE`)で両者の頭上に短いセリフの吹き出しが出て(`BirdState.chatLine`/`chatLineSetAt`)、`CHAT_PAUSE_TICKS`(3秒)その場で立ち止まる(`BirdState.chatPauseTicks`、`activity: 'chatting'`)。当初は吹き出しを出すだけで鳥はそのまま動き続けていたため、何が起きたのか分からないという実機フィードバックがあり、実際に立ち止まる演出を追加した。
    - **ご機嫌度との連動**: 寄り道・遊ぶ・雑談はいずれも、ご機嫌度(`happiness`)が`HAPPINESS_LOW_THRESHOLD`(40)以下の時に発生率が上がる——「退屈している時ほど、それらしい行動が増える」という自然な発生条件にしてある。ただし雑談は当初、ご機嫌度による倍率だけをベースの発生確率に掛ける実装だったため、ご機嫌度が良好な(=よくある)状態だと逆に最も発生しにくくなってしまう実機フィードバックがあった——ご機嫌度に関わらず一定確率で発生するベース値(`CHAT_CHANCE_BASE`)に、ご機嫌度が低い時だけ加算するボーナス(`CHAT_CHANCE_LOW_MOOD_BONUS`)を足す方式に変更し、あわせて近接判定の距離(`CHAT_PROXIMITY_DIST`)も、鳥同士の押し合い判定(`MIN_BIRD_DISTANCE`)とほぼ同じ狭さだったため広げた。5分程度のプレイで最低1回は発生する頻度を目安にした一次調整値であり、実機で様子を見て要再調整。
    - **ひらめきシステム**: 遊んでいる間、毎ティック独立して2種類の抽選を行う。①**ステータス上昇**(発生確率`INSPIRATION_STAT_CHANCE`=中程度): HP・攻撃力・防御力・素早さ・運のいずれかが少し(`INSPIRATION_STAT_GAIN`=1、HPのみ`INSPIRATION_HP_GAIN`=3)恒久的に上昇し、生活ログに記録されつつ、鳥の頭上に「💡ひらめいた!」の軽い吹き出し(雑談と同じchatLine機構を流用)が出る。②**スキル獲得**(発生確率`INSPIRATION_SKILL_CHANCE`=かなり低い、①より優先して判定): `data/skills.ts`のBIRD_SKILL_DEFSからまだ持っていないスキルを1つ選び、`BirdState.skills`(永続化対象、`BirdWallet.skills`)に追加する。スキルは装備・ジョブとは別枠の恒久効果で、実装上は装備のstatBonusと全く同じ仕組み(`game/birdStats.ts`のgetEffectiveStatsが装備ボーナスに続けてスキルボーナスも合算)で扱われる——新しいドロップ率ロジックなど別種の仕組みを増やさないための意図的な選択。用意したサンプルは4種(体力全開=攻撃力+1、頑丈な体=防御力+1、俊足=素早さ+1、幸運体質=運+2)。依頼書の例では幸運体質を「ドロップ率アップ」としていたが、ドロップ率という仕組み自体がまだ存在しないため、代わりに運の数値ボーナスとした(将来ドロップ率ロジックを追加する際の拡張候補)。スキル獲得時は`RecipeUnlockModal`と同じ形の目立つ通知(`SkillUnlockModal`、「💡◯◯がひらめいた!新しいスキル「◯◯」」)が表示される——他の非永続キュー(recruitmentEvents/recipeUnlockEvents)と同じ`skillUnlockEvents`のキュー方式で、TownScreenの他モーダルとの排他制御(実機で複数回発生した「モーダル二重表示でタップ無反応になる」不具合の対策)にもそのまま組み込んである。獲得済みのスキルは🐦ステータスカードにも💡バッジで一覧表示される。
    - **家でのお昼寝(追加調整)**: 常にちょこまか動き続けて落ち着きがないという実機フィードバックを受けて、休憩カテゴリ(`ActivityCategory: 'rest'`)の新しい選択肢として「家でお昼寝」(`activity: 'napping'`、頭上に😴)を追加した。既存の川・池での息抜きや街の散歩よりも大幅に長い`NAP_DWELL_TICKS`(8秒)だけ家でじっとする、意図的に緩やかな行動。満腹度・ご機嫌度がともに`NAP_GOOD_MOOD_THRESHOLD`(60)以上の「機嫌の良い」状態だと選ばれる確率(`NAP_CHANCE_GOOD_MOOD`)が、そうでない時の基本確率(`NAP_CHANCE_BASE`)より大きく上がる——「眠いから仕方なく」ではなく「機嫌が良いからのんびりする」という自発的な休憩として発生する。
    - **建物の視認性(追加調整)**: 公園・水浴び場をはじめ、建設済みの建物がアイコンだけで名前表示が無く、マップ上で何の建物か分かりにくいという実機フィードバックを受けて、区画スプライトの下にごく小さな名前ラベル(`WorldMap.tsx`のplotBuildingLabel、建物名/店名)を追加した。プレイヤー・鳥双方の行動自体は元々仕様通り動いていたため(建設フロー・マップ描画とも建物種別を特別扱いしていない)、今回は表示側だけの改善。
23. **建物スプライトの導入**: 役場(発展段階5種)・餌屋/道具屋/武器屋/防具屋・商人の出店・公園/水浴び場・鳥の家(4色)・街の柵を、これまでの絵文字表示から専用の描き下ろしイラスト(`assets/buildings/`)に差し替えた。素材は依頼で提供された1枚のリファレンスシート(16項目+柵8種のグリッド)から、各セルの近白色/市松調の背景(実データはアルファ透過ではなくRGB画像だったため)を「画像の縁から連結した明るい領域」をアルファ0にするフラッドフィル法(`scipy.ndimage.label`で背景色に近い画素の連結成分を検出し、外周に接しているものだけを透過化——window/doorなど孤立した明るい部分は外周と繋がっていないため透過されない)で自動的に切り出し、さらに各セルのバウンディングボックスまでトリムして個別のPNG(`data/buildingImages.ts`が名前付きでrequireするレジストリ、tileImages.tsと同じ方式)にした。一部のセル(6〜10番・15・16番)はラベル文字が画像の左上に重なる形でレイアウトされており、単純な矩形マスクでは店名によって除去しきれない/建物を削ってしまう恐れがあったため、行ごとの背景率プロファイルからラベル文字と建物本体の間の“谷”になっている行を探して、そこでクロップ位置をずらすことで対応した。役場・鳥の家は発展段階/個体によって画像の縦横比が大きく異なる(ボロ役場は横長、トロロ自然保護本部は縦に高い塔付き)ため、`WorldMap.tsx`側は中央合わせではなく下端合わせ(`justifyContent: 'flex-end'`)でボックス内に配置し、どの画像でも「地面に立つ位置」が揃うようにしてある。街の柵は柵パネル画像1種(`fence_wood_short.png`)を、ゾーン楕円上の各柵ポスト位置での接線角度(`Math.atan2`でパラメトリック楕円の接線ベクトルから算出)だけ回転させて敷き詰め、曲線に沿った柵らしい見た目にした——リファレンスシートには木/石/生け垣・直線/角/門など柵の種類が8種類含まれているが、曲線に沿って種類ごとの継ぎ目を正しく配置するには本格的なセグメント配置ロジックが必要になるため、今回は依頼の「まずは1〜2種類の簡易な実装でも構わない」という許容範囲に沿って1種類のみ採用した(残り7種も`assets/buildings/`に切り出し済みで、将来使う場合の追加コストはない)。倉庫(共有倉庫)・依頼掲示板の2点は画像を切り出しただけで、対応するマップ上の建物枠が現状存在しない(共有倉庫はプレイヤーの素材倉庫、依頼掲示板は下部の「📋依頼」ボタンとして、どちらも独立したマップ建造物ではなくUIパネルとして実装されているため)ため、今回は組み込みを見送った。絵柄について: 建物素材はやや陰影のある写実寄りのタッチで、鳥キャラクター(フラットな塗りの2頭身)とはテイストに差があるが、彩度・配色自体はパステル寄りの街並みと大きく衝突しないため、今回はそのまま組み込んだ——実機で見た際に違和感が強いようであれば、別途相談の上で建物側の彩度・コントラスト調整や鳥キャラ側の見直しを検討する。
24. **街レイアウトの密集配置化**: 前項の建物スプライト組み込み後、実機で見ると建物同士の間隔が空きすぎて「間延びした」印象になっていたため、区画グリッド・ゾーン楕円・柵・固定装飾(家/商人)の座標を全面的に詰め直した。区画1マスの間隔(`townGrid.ts`のCELL_W/CELL_H/OUTER_STEP_X/OUTER_STEP_Y)を約1/3(65px間隔)へ縮小——このとき、リング3(外周)の張り出し幅(OUTER_STEP)は元々「リング2からさらに1マス分より少し狭く」してキャンバスからはみ出さないようにしていたが、セル自体が縮んだ今はその制約が不要になっていたことに気づかず一度そのまま縮めてしまい、リング2/3間の区画が44pxの見た目サイズに対して26pxしか間隔がなく約18px重なるバグを検証スクリプトで検出——OUTER_STEPをCELL_W/CELL_H同値(=通常の1マス分)に戻して解消した。ゾーン楕円(`TOWN_ZONE_RADIUS`)も新しいグリッド密度に合わせてrx=0.22→0.235/ry=0.145→0.152へわずかに拡大(フィールド側の敵・採掘ポイントとの最短距離は依然24%の余裕あり)。鳥の家・商人の出店は区画グリッドの数式から独立した固定座標だったため、区画を詰めた分だけ区画と衝突するようになり、単純な「中心距離−半径の和」という円モデルでの再配置ではプラスの余裕が出たにも関わらず、実際の当たり判定は矩形(Pressableのwidth/height)であるため対角線方向にオフセットした2つの四角は円モデルより衝突しやすい、という見落としに気づき、矩形同士の実際の重なり量で再計算——家(36px角)は隣接区画4つとちょうど等距離になる格子の「目地」上に置くのが数学的に最良で、それでも約7.5px分の浅い重なりが避けられないと判明(区画44px+外周ステップ65pxという寸法から導かれる下限で、区画をさらに小さくしない限り解消不可能)。これはタップ対象の大部分が独立して機能する程度の浅い重なりのため、以前からの「リング3隅の区画がゾーン楕円から少しはみ出る」という許容例と同種の妥協として受け入れた。商人の出店は表示ボックス自体を旧来の56px幅(他の汎用スプライトと共通の`styles.sprite`)から32×42pxの専用ボックスへ縮小した上で再配置し、重なりゼロを達成。柵(`fenceNodes`)はポスト数を20→48へ増やし(1周の弧長に対してパネル幅30pxよりわずかに密な間隔にすることで、隙間なく繋がって見えるように)、柵ポストは非インタラクティブ(pointerEvents="none")なため衝突検証は不要。装飾(`TOWN_DECOR`)は新しい柵の内側に収まるよう既存4点を再配置し、既存のモチーフ(🪷=池、LEISURE_SPOT_DEFSの池と同じ絵文字)を再利用した4点を役場周辺の空きスペースに追加した。検証は今回も実機スクリーンショットが撮れないため、実際のレイアウト計算式と切り出し済み建物素材を使ったPython/PIL静的モックアップで最終確認した。
25. **見た目装備(コスチューム)システムの新設**: 添付の参考シート(タイトルは「ビビ専用装備一覧」だったが、実際は4羽共通で使い回す想定という依頼内容の指摘を受け、表記の誤りとして扱った)から、既存のステータス装備(武器・防具・帽子・盾、`EquipSlot`)とは完全に別の、見た目のみのコスチュームスロットを新設した。データ面は`types.ts`に`CosmeticCategory`(着ぐるみ/おしゃれな服/かわいい服/イベント/テーマ/季節の6種)、`BirdState.cosmeticId`/`BirdWallet.cosmeticId`(`string | null`、1羽につき1着まで)を追加し、`data/cosmetics.ts`に`CosmeticItemDef`(id/name/category/imageAsset)のカタログを作った——依頼の「まずは各カテゴリから数点ずつのサンプル実装で構わない」に沿って、6カテゴリ×2点=12点のみを参考シートから切り出した(`assets/cosmetics/`、建物スプライトの時と同じ背景除去+バウンディングボックストリムのPythonパイプラインを流用)。着せ替えは`useWorldStore`の`setCosmetic(defId, cosmeticId)`(常時呼べる直接更新アクション、`favoriteTreasure`と同じ「tickを待たずにその場でworld state を更新する」パターン)で行い、コスト・所持数のチェックは一切なし(入手方法の設計は依頼のスコープ外)。表示は`CharacterAvatar`に新しい`cosmeticId`propを追加し、コスチューム画像を「本体スプライト(`BIRD_BASE_SPRITES`)の上に重ねる」のではなく丸ごと差し替える形にした——参考シートの画像自体が(`assets/birds/README.md`と同じ)256×256・中央揃え・下部余白付きの「鳥1羽の全身イラスト」として描かれているため、本体との重ね合わせ位置調整が一切不要になる。着せ替えUIは`BirdRosterModal`の各鳥カードに、水平スクロールのサムネイル一覧(+「なし」で解除)を追加し、タップした`AnimatedPressable`がそのまま`setCosmetic`を呼ぶ。素材面での制約: 参考シートを実際に切り出したところ、「おしゃれな服」「かわいい服」の2カテゴリだけは(着ぐるみ・イベント・テーマ・季節と違い)服単体のイラストで、鳥本体が描かれていないことが判明した——本体を丸ごと差し替える今回の実装方式だと、この2カテゴリを着せた鳥は見た目上「服だけが浮いて鳥が消える」表示になる。これは切り出しミスではなく参考シート側の作画の不統一によるものなので、そのまま黙って組み込むのではなく明示しておく——別の素材への差し替え、または鳥本体スプライトへの服の合成(スタイルの違いから位置合わせに別途調整が必要)が必要であれば、追って相談。
26. **見た目装備システムの修正: 全カテゴリを「本体合成方式」に統一**: 前項出荷後の実機報告で、上記の「服単体で鳥が描かれていない」問題(おしゃれな服・かわいい服)に加えて、逆側の問題も見つかった——着ぐるみ・お祝い・テーマ・季節の8点は、参考シートが「ビビ専用」だった名残でビビ自身の顔・配色が絵にそのまま焼き込まれており、他の3羽がこれを着ると(本体を丸ごと差し替える実装だったため)その鳥自身ではなくビビの顔が表示されてしまっていた。原因は共通(カテゴリごとに素材の描かれ方が統一されていなかったこと)なので、全12点を「鳥本体を含まない、コスチューム部分のみの絵」に揃え、各鳥自身の`BIRD_BASE_SPRITES`の上に重ねて合成表示する方式に統一した。8点の焼き込み除去は、色ベースのフラッドフィル(建物スプライトの背景除去で使った手法)だと「残したい部分(着ぐるみのフード等)」と「消したい部分(素の鳥の顔・体)」の色味が重なりすぎて誤って両方消えてしまう/両方残ってしまう事故が起きたため、座標ベースの楕円・矩形マスク(`scipy.ndimage`の`binary_dilation`で塗り残しの輪郭線も一緒に消す)に切り替え、各画像ごとに目視で穴の位置・大きさを調整した——例えば「顔だけが出る」着ぐるみ(ペンギン、雪だるま等)は顔部分だけを楕円でくり抜き、「フードの下に素の体が続く」タイプ(おおきなインコ、ひまわり等)はフード部分だけを残して下半分を丸ごと消す、サンタケープのような「縁取りだけが衣装」タイプは中央を消して外周のケープ部分だけ残す、という具合に各画像の構図に応じてマスク形状を変えた。位置合わせの基準点は`assets/birds/README.md`の256×256キャンバス規約(足裏基準線y=229、中央x=128)を流用し、`data/cosmetics.ts`の`CosmeticItemDef`に`widthFrac`/`heightFrac`/`centerXFrac`/`centerYFrac`(256キャンバスに対する比率)を追加——ビビの本体スプライトに実際に重ねて位置を目視調整し、配色の異なる別の鳥(ハク)に同じ数値を適用しても違和感なく揃うことを確認した(4羽とも同じキャンバス規約で作られているため)。`CharacterAvatar`は本体スプライトの上に`position: 'absolute'`でコスチューム画像を重ねるよう変更(以前の「本体を丸ごと差し替え」から「本体の上にレイヤーする」への転換)。`BirdRosterModal`の着せ替えサムネイルも、素のコスチューム画像ではなくその鳥自身の`CharacterAvatar`(本体+コスチューム合成済み)を表示するよう変更し、選択プレビューが実際の見た目と一致するようにした。検証はPython/PILで12点×4羽=48通りの合成を実際にレンダリングし、目視で全羽が自分の顔・配色で表示されることを確認した。
27. **見た目装備の合成位置調整 + 段階的な入手システム**: 前項出荷後の実機報告で、合成位置(`widthFrac`等)を256×256の何もない透過キャンバス上でしか検証しておらず、実際のアバターボックス(`WorldMap`の`BirdSprite`は44px、しかもすぐ外側にお疲れ絵文字😤・ツルハシ⛏️のバッジがtop:-10/-8で置かれている)では窮屈すぎたり隣接バッジと衝突しうる余白だったことが判明した。対応として、①`CharacterAvatar`のアバターボックスに`overflow: 'hidden'`を追加(以後どんな配置ミスがあってもボックス外には絶対に漏れない安全策)、②データ形式を依頼の指定通り`offsetX`/`offsetY`/`scale`(+画像自身のアスペクト比`aspect`)に整理、③全12点のスケールを一律85%に縮小しつつ、実際の44pxボックスでクリッピングをシミュレートしたPython合成で再検証——2点(おおきなインコ、ひまわり)だけ装飾の先端が数px切れる程度で着地させた(致命的な破綻ではないため許容)。

続けて、コスチュームの段階的な入手システムをフェーズ8のレシピ解放の仕組みを流用して追加した。初期状態で着られるのは`costume_parrot`(おおきなインコ)と`outfit_flower_dress`(お花のワンピース)の2点のみ(`CosmeticItemDef.unlockedByDefault`)。残りは以下の4ルートで入手する:
- **見つける/ドロップ**: `game/cosmeticUnlocks.ts`の`maybeAwardCosmeticTicket`が、採取成功時(`COSMETIC_FIND_CHANCE`)・討伐時(`COSMETIC_DROP_CHANCE`)にそれぞれ小確率で「まだ持っていないコスチュームのチケット」を1枚倉庫に加える——フェーズ8のレシピ発見ルート(`RECIPE_GIFT_CHANCE`/`RECIPE_COMBAT_CHANCE`)と全く同じ発生源・頻度感で実装した。
- **作る**: `data/costumeRecipes.ts`に`CostumeRecipe`(既存の`CraftingRecipe`と同形、結果が`ItemId`ではなく`cosmeticId`)を新設し、解放状態は既存の`useRecipeStore`にそのまま相乗り(レシピIDは単なる文字列なので、アイテムレシピと同じ`unlockedRecipeIds`配列で問題なく共存できる)。さらに、レシピの自動発見ロール(`game/recipeUnlocks.ts`)自体もアイテム・コスチューム両方のレシピから選ぶよう一般化したため、「レシピを見つけた!」の報酬がコスチュームのレシピになることもある(商人の販売レシピは`ItemDef`前提のUI実装のため、そちらはアイテムレシピのみのまま)。加工には`usePlayerStore.craftCosmetic`を新設——素材を消費するが、倉庫のアイテムではなく`useCosmeticStore`のチケットを1枚生成する点だけが通常の`craftItem`と異なる。
- **贈る**: 新設した`CostumeCollectionModal`(トップバーの🎁ボタン)から、所持中のチケットを選んで4羽の中から贈り先を選ぶと、そのコスチュームが全鳥共通で解放される(コスチューム自体が共通仕様のため、「贈り先を選ぶ」はあくまで演出で、実際の効果は常にグローバル解放)。このモーダルでは加工可能なレシピの一覧・加工ボタンもまとめて扱う。

38. **着ぐるみ(スペシャル)一式の差し替え + 3点追加**: ユーザー側で着ぐるみ用参考シートの該当行を描き直したものを受け取り、差し替えた。従来の`costume_parrot`/`costume_penguin`は顔穴の中に「見本の鳥」自身の顔・頬・くちばしの一部がうっすら焼き込まれており、item 36の`facePatch`をどれだけ精密に測っても、その焼き込みが完全一致でない限りごく一部だけ透けて見えてしまう(item 30/36で追った「残存する顔の断片」バグの根本原因)——新しいシートはこの行を丸ごと描き直し、顔穴を単なる白ベタ塗りにした上で(アルファ抜きの手間が要らず、確実に透過に切り出せる)、対象をおおきなインコ・ペンギンの2点から参考シート本来の5点(+シマエナガ・恐竜(グリーン)・ユニコーンを追加)に拡張し、行のタイトル表記の誤り(「ビビ専用コスチューム」——ユーザーの指摘通り、全鳥共通で実際は専用ではない)も合わせて解消される形になった。切り出しは、まずセル同士を連結成分検出で分離し、次に各セル内の顔穴を「ローカル分散が周囲の毛並み・鱗のテクスチャよりずっと低い、明るい塗り」として検出する方式にした——白に近い体色を持つシマエナガでは単純な明度しきい値だけでは体全体まで拾ってしまい穴だけを切り出せなかったため、この分散ベースの判定に切り替えて解決した(検出後、穴の内側だけがアルファ0の独立領域になっているかを連結成分解析で機械的に検証済み)。scale/offsetYは5点とも共通の値(0.6973/-0.0781、以前のインコ・ペンギンの調整値をそのまま踏襲)を使い、`facePatch`は各アイテムごとに実測した穴の中心・半径から個別に算出。4羽×4サイズ(48/44/40/32px)×5アイテムの全組み合わせをPythonでの再現レンダリングで確認し、どのアイテムも顔パッチが穴からはみ出さず・隙間もできないことを確認済み。新規3点は既存の「アンロック済みでないコスチュームからランダムに1点選んでチケットを配る」汎用の入手ルート(`game/cosmeticUnlocks.ts`)がカタログを直接参照する実装のため、追加のレシピ・ドロップ登録なしでそのまま入手候補に加わる。画像ファイルは新しい参考シートの解像度が旧アセットよりかなり大きかったため、実際の表示サイズ(最大48px)に対して十分な余裕を持たせつつ幅180pxへ縮小し、アプリのバンドルサイズ増加を抑えた。

39. **顔パッチのつぶれバグ修正**: item 38直後の実機報告「かおがつぶれてる」を受けて調査したところ、`fullBody`コスチュームの顔パッチが縦横比の歪んだ状態で表示されるバグが見つかった。`FACE_PATCH_CROP`(鳥本体の256×256スプライトから顔まわりを切り出す共通のクロップ範囲)がこれまで横0.6×縦0.42という非正方形の矩形だったのに対し、`CharacterAvatar.tsx`はこの範囲を`resizeMode:'stretch'`で正方形の顔パッチコンテナに収まるよう引き伸ばしていた——正方形の元画像(鳥本体スプライト)を非正方形の範囲で切り出し、それを正方形のコンテナに強制的に当てはめる処理は、必然的に非一様な引き伸ばし(縦横で拡大率が異なる歪み)になり、これが「つぶれ」の直接原因だった。`FACE_PATCH_CROP`を正方形(0.48×0.48、`x0:0.26/y0:0.08/x1:0.74/y1:0.56`)に修正——4羽それぞれの`base.png`を行ごとの不透明幅プロファイルで調べ、頭部の幅がプラトーになる範囲(肩・羽が広がり始める手前まで)を正方形でちょうど収める大きさ・位置を実測して決定した。修正後、4羽×4サイズ×5アイテム(item 38の着ぐるみ一式)の全組み合わせをPythonでの再現レンダリングで再確認し、歪みのない自然な丸顔になることを確認済み。

40. **顔パッチの比率調整 + 服・アクセサリー系3点の差し替え**: item 39で歪みは直ったが「もう少し見本と同じ顔の比率になるように調整してほしい」という追加要望を受けた。参考シートでは顔穴を覗く顔がほぼ隙間なく穴いっぱいに映っているのに対し、実装では顔パッチの直径を穴の直径の1.08倍(はみ出しを隠すための最小限の余裕)に抑えていたため、穴の中に小さな顔がぽつんと浮いて見える状態になっていた——倍率を約1.5倍に引き上げ、4羽×4サイズ×5アイテムの全組み合わせで、コスチューム本体のシルエットからはみ出さないことを確認しながら再検証した。あわせて、item 34で「本当に襟が高すぎて顔が隠れていた」と判明していた3点(セーラー服・リーフチュニック・ふわふわセーター)について、ユーザーが作り直した新しい参考シートを受け取り差し替えた——新シートは着ぐるみ行(item 38)と同様、襟の内側の「覗き穴」が実際には単色のベタ塗りで、透過ではなかったため、まず背景(ぼかしたグラデーション背景で、単色ではないため輪郭のエッジ検出+外周からの塗りつぶしで除去)を切り離し、次に襟内側のベタ塗り領域を色類似度による塗りつぶし(アイテムごとに色が違う——ホワイトのボディに対しホカホカセーターは黄土色、リーフチュニックは濃い緑、セーラー服は灰青、といった具合)で検出して透過化した。`overlay`型はfullBody型と違い鳥本体スプライトをそのまま表示するため、各服のoffsetX/offsetYは「新しく切り出した穴の位置」を「4羽の実際の目線の高さ(頭が大きいハク・トロロに合わせた妥協値、box比率0.36)」に合わせる形で計算し直した(旧版のoffsetYは古い——襟が高すぎた——絵に対する値だったため、そのまま流用せず全て再計算)。

42. **着ぐるみ系(fullBody)、顔穴に鳥本体の「頭頂部の色」が帯状に映り込むバグ修正**: item 41の後も「全部ずれる」という強い実機報告を受けたため、今回はまず送っていただいたスクリーンショットを実際にピクセル単位で切り出して調べるところから始めた。結果、item 40/41で対応した`overlay`型の3点(セーラー服・リーフチュニック・ふわふわセーター)は実は問題なく正しく表示されていることを確認できた——ズレの実体は`fullBody`型(着ぐるみ系5点)の方で、ユニコーンを着たトロロの顔穴の上部に、顔の色(オレンジ)ではなく頭頂部の羽の色(トロロの場合は緑)が三日月状に映り込んでいた。原因は`FACE_PATCH_CROP`(item 8で正方形化した「頭全体」のクロップ範囲、y0:0.08〜y1:0.56)にあった——この範囲は頭全体を含む分、頭頂部の羽毛(顔の色に変わる前の部分)も含んでしまっており、正方形のプレビューで見ている分には目立たなかったが、実際の描画は円形にクリップされるため、円の一番上の弧はほぼこの「頭頂部の帯」だけを映すことになり、そこがくっきり別の色として浮いて見えていた。4羽それぞれの頭頂部から顔の色に変わる境界のy座標を実測(トロロが最も遅く y≈0.22〜0.24、ハクは頭頂部と顔がどちらも白いため元々目立たない)し、その境界より下だけを含む一回り小さい正方形(0.32×0.32、y0:0.20〜y1:0.52、目線の高さ0.36を中心に据えたまま)に縮小した。`facePatch`のscale/offsetX/offsetYは穴の位置合わせ用の値でクロップ内容とは独立のため変更不要——4羽×4サイズ×5アイテムの全組み合わせで頭頂部の色の映り込みが完全に消えたことを確認済み。今回の教訓として、以降は「実機のスクリーンショットを先にピクセル単位で確認してから直す」順序を徹底する。

43. **着ぐるみの顔穴を拡大 + 新しい服6点の追加**: 「着ぐるみ、もう少し横長、縦ももう少し顔出す部分大きくできる?」という要望と、新しく描いた服6点の参考シートを受けての対応。①着ぐるみ(スペシャル)5点それぞれの実際の透過穴を、中心はそのままに横方向135%・縦方向115%に拡大(頭の輪郭からはみ出さないことを確認済み)。この「実際にPNGへ焼き込まれた穴」と「CharacterAvatar.tsx側で描く顔パッチ」は連動して大きくしないと意味がない(片方だけ大きくしても、はみ出た分が着ぐるみ本体の不透明なファブリックに隠れるか、逆に穴だけ大きくなって顔が小さく浮くかのどちらかになる)ため、両方を同時に変更した。`facePatch`のデータ形も、正方形前提の`scale`単一値から、横長の穴形状に合わせて`width`/`height`の2軸指定に変更し、`CharacterAvatar.tsx`側は`borderRadius: Math.min(width,height)/2`という「スタジアム(角丸長方形)」型のクリップに変更——完全な楕円はReact Nativeのborderradiusでは表現できないが、この程度の縦横比ならスタジアム型で見た目上ほぼ違和感なく近似できる。`FACE_PATCH_CROP`(顔を切り出す共通範囲)も正方形から横長の矩形に変更したが、item 42で頭頂部の色が映り込まないよう調整したy0(0.20)は変えず、y1を下げる・x0/x1を広げる方向でのみ拡張し、頭頂部の色の再発を防いだ。②新しい参考シート(セーラー襟・ピンクパーカー・葉っぱのケープ・星空のケープ・ひまわりシャツ・チェックのケープの6点)は、背景が「本物のアルファ透過」ではなく市松模様(チェッカーボード)をRGBピクセルとして直接焼き込んだもの(前回までのぼかしグラデーション背景ともまた違うパターン)だったため、輪郭のエッジ検出方式だとチェッカーの格子自体を壁と誤検出し、背景が無数の1マス単位の孤立領域に分断されて外周と繋がらず、うまく背景と判定できなかった——色ベースの判定(グレースケールに近く、かつチェッカーの2色のいずれかに近い)に切り替え、タイル同士の継ぎ目のアンチエイリアス部分まで拾えるよう許容範囲を広めに取ることで解決した(狭すぎると継ぎ目部分が「前景」判定されて格子状のノイズとして全タイルを繋げてしまっていた)。6点のうち「葉っぱのケープ」は肩掛け型で胸元が最初から完全に開いた作りだったため顔穴の切り出しは不要(既存のevent_santa_capeと同じ考え方)、残り5点は既存の襟の切り出しと違って穴の位置を示す塗り分けが元絵に無かったため、各アイテムの襟の形を見ながら手動で穴の位置・大きさを決め、item 41の教訓(穴の中心を目線にぴったり合わせると目が隠れる)を最初から織り込んで下寄りにオフセットした。6点とも4羽×4サイズでの再現レンダリングは確認済みだが、既存カタログの他アイテムと違って一度も実機での動作確認を経ていない新規追加のため、他のアイテムより位置調整の再修正が必要になる可能性が高い。

44. **item 43の新規服5点、目にかぶるバグ修正 + 着ぐるみ顔穴のさらなる拡大**: 「上すぎる!!あと着ぐるみはいい感じ、あとほんとに一回りだけ穴をデカくして」という実機報告(チェックのケープが襟で目を完全に覆っているスクリーンショット付き)を受けての対応。まさにitem 43の文末で懸念していた「実機での再修正が必要になる可能性」がそのまま的中した形——item 43で新規追加した5点(セーラー襟(ネイビー)・ピンクパーカー・星空のケープ・ひまわりシャツ・チェックのケープ)のoffsetYは、各アイテムの襟穴の実測位置から数式的に算出した値だったが、これがことごとく浅すぎ、穴の開口部が目のライン全体を覆ってしまっていた(最悪だったのがスクリーンショットに写っていたチェックのケープ)。今回は数式に頼るのをやめ、item 41/42で確立した「実際に出荷済みアセットを複数のoffsetY候補で実寸(120px)レンダリングし、目で比較して選ぶ」方式に統一し、4羽全体で確認: セーラー襟(ネイビー) 0.10、ピンクパーカー 0.16、ひまわりシャツ 0.10、星空のケープ 0.16、チェックのケープ 0.18(スクリーンショットで最も酷かった分、動かす量も最大)。一方「着ぐるみはいい感じ」という一文はitem 42/43の着ぐるみ側の直し自体は正しかったことの確認でもあり、そのうえで「一回りだけ穴を大きく」という追加の小幅な要望だったため、着ぐるみ(スペシャル)5点それぞれのすでに拡大済みの透過穴を、中心はそのまま各辺方向にさらに16%(rx/ry×1.16)拡大——`FACE_PATCH_CROP`自体(共通クロップ範囲)は変更せず、各アイテム側の`facePatch`(width/height/offsetX/offsetY)だけを新しい穴のサイズ・位置に合わせて再計算した。最初オウムだけ他の4点よりも拡大率を上げると頭の輪郭からわずかにはみ出す(item 42と同じ境界チェックで検出)ことが分かったため、5点とも同じ1.16倍に揃えて安全マージンを確保した。

bubbleを流用)と、拗ね始めた瞬間の活動ログ1行を表示。さらに`HOUSELESS_WARNING_TICKS`(約1時間後)を超えると`HouseWarningModal`で「このままだと旅立ってしまうかも」の警告(「🎁プレゼントを渡す」ボタンから`GiftBirdModal`へ直接つながる)、さらに`HOUSELESS_LEAVE_TICKS`(さらに約2時間後、警告からの猶予は意図的に長め)を超えると`isRecruited`をfalseに戻す形で街を旅立つ(HP0時と同じ「深刻にしない」方針で「旅立ってしまいました」という軽い表現、`HouseDepartureModal`)。**プレゼント**(`GiftBirdModal`、`BirdRosterModal`の🎁なだめるボタンからも直接開ける)は倉庫の品物を1つ渡す簡易的な仕組みで、ご機嫌度を回復しつつ`houselessTicks`を0にリセット——家を与えるわけではなく「なだめて時間を稼ぐ」という位置づけで、その後も家がなければ再び拗ね始める。イベントの一度きり通知は「前のtickの値がしきい値以下・今のtickの値がしきい値超え」というライブtick限定の単純な比較で実現(オフライン中はこの`houselessTicks`自体を進めない設計のため、アプリを閉じている間にしきい値をまたいでも再起動時に二重発火しない)。しきい値越え・ギフトによるリセット後の再発火・旅立ち後の状態リセットは、実際のstoreを介さない軽量シミュレーションスクリプトで動作を確認済み。`npx tsc --noEmit`・`npx expo export --platform ios`とも確認済み。

Expo Go を使えば、Xcode も Apple Developer 登録も不要でiPhone実機に反映して試せます。

### 事前準備(PC側、1回だけ)

1. **Node.js** をインストール(LTS版。 https://nodejs.org/ )
   - 確認: `node -v` でバージョンが表示されればOK
2. **git** をインストール(https://git-scm.com/ )
3. このリポジトリを clone

   ```bash
   git clone https://github.com/botaou/tororo-dungeon.git
   cd tororo-dungeon
   git checkout claude/idle-dungeon-game-prototype-pj9axt
   ```

4. 依存パッケージをインストール

   ```bash
   npm install
   ```

### 事前準備(iPhone側、1回だけ)

- App Store から **Expo Go** アプリをインストール

### 起動して確認するたび

1. PCとiPhoneを**同じWi-Fi**に接続する
2. PCでプロジェクトフォルダに入り、開発サーバーを起動

   ```bash
   npx expo start
   ```

3. ターミナルにQRコードが表示されるので、iPhoneの**カメラアプリ**でスキャン → 「Expo Goで開く」の通知をタップ
4. Expo Goが起動し、アプリが実機で動きます

コードを変更して保存すると、実機側は自動でリロードされます(Fast Refresh)。確認が終わったらターミナルで `Ctrl+C` して開発サーバーを止めればOKです。

### うまくいかない時

- QRコードが読み取れない/繋がらない → PCとiPhoneが同じWi-Fiか確認。会社・大学のWi-Fiなど端末間通信が制限されたネットワークでは失敗しやすいので、自宅Wi-Fiや共有したスマホのテザリングを試す
- それでも繋がらない → `npx expo start --tunnel` (別ネットワークでも動くが、初回に `@expo/ngrok` の自動インストールを求められます)

## コード構成

```
src/
  types.ts              共有の型定義（BirdState, JobRequest, WorldState, TownPlotDef など）
  data/
    characters.ts       4羽の性格・ステータス定義
    world.ts             街の位置、敵・採掘・お宝の定義（常設フィールド）。一部の敵・採掘ポイントは`minTownLevel`付きの「奥地」コンテンツで、街レベルがそこに達するまでAIのターゲットにも描画対象にもならない
    materials.ts          素材ID→ラベル・アイコンの対応表
    marketPrices.ts        鳥から素材を買い取る際の固定レート表
    items.ts               モンスタードロップ・加工アイテム・餌屋の商品カタログ(ID→名前・ジャンル・アイコン・購入価格、通常商品はrestockCost付き)。`itemType: 'craft'|'convertible'`で加工品/換金専用アイテムを区別。CONVERTIBLE_ITEM_IDS・MERCHANT_COMMON_ITEM_IDS・MERCHANT_RARE_ITEM_IDSを導出済み
    recipes.ts              加工レシピのカタログ(必要素材→完成アイテム。武器・防具と高級餌。換金アイテムは加工不可)。各レシピは`unlockedByDefault`を持ち、最初から使えるのは3個のみ(残りはuseRecipeStore経由で入手するまで加工パネルに出ない)
    shops.ts                お店の種類の定義(道具屋(帽子・盾)・餌屋・武器屋・防具屋の4種。道具屋・餌屋は常設、武器屋・防具屋は建設するまで存在しない。換金アイテムはどの棚にも並ばない)
    townGrid.ts           街の土地グリッド（48区画、うち外周1リング24区画は`minTownLevel:3`で街レベル3まで解放を試みることすらできない）の位置・解放コスト定義、常設ショップ2件の区画ID、商人の出現位置(MERCHANT_SPOT)、街の発展ポイント(developmentPoints)から街レベル(5段階の名称・絵文字・しきい値=TOWN_LEVEL_DEFS)を導出するgetTownLevel/getTownLevelDef、土地解放1回あたりの付与ポイント(PLOT_UNLOCK_DEVELOPMENT_POINTS)・建設1回あたりの付与ポイント(CONSTRUCTION_DEVELOPMENT_POINTS)、街レベルに応じて広がる街エリアの楕円半径を返すgetTownZoneRadius。フェーズ11で追加したgetAllAmenityPositionsは、建設済みの公園・水浴び場の位置一覧をgetAllShopPositionsと同じ発想で返す（固定枠がないので走査するのは建設済み区画のみ）。常設ショップ2件は、通常のリング1グリッド間隔ではなく専用の近め固定オフセット(SHOP_AXIS_OFFSET)に配置——街エリアの楕円が一番小さい街レベル1でも余裕を持って内側に収まるようにするため(実機で店がゾーン境界からはみ出て見える不具合の修正)
    buildingOptions.ts     解放済み・更地の区画に建設できる建物のカタログ(BUILDING_OPTIONS)。各項目はゴールド+素材1種類のコストと、実際に機能する店舗(道具屋/餌屋の出張所は既存店舗と在庫を共有、武器屋・防具屋は新規の店舗種別として初めて成立する)か、売買機能を持たない花壇・公園・水浴び場(フェーズ11。公園・水浴び場は鳥が「遊ぶ」行動の目的地になる)かを表すbuildingKind/shopKind情報を持つ
    jobPresets.ts           依頼掲示板のプリセットカタログ(採取/討伐/クラフト/商人納品の4種、対象+数量+報酬ゴールド・経験値・街の発展ポイント・街評価)。プレイヤーの手動投稿(`postRequest`)が参照する依頼データソース(以前はtickの自動補充もここから選んでいたが廃止済み)。種別ごとにアイコン・ラベルを返すdescribeJobTargetヘルパーもここ
    houses.ts              鳥ごとの家の位置(役場を中心にした小さな菱形配置。街エリアの最小ゾーン楕円(街レベル1)に対し余裕を持って内側に収まるよう配置——以前は4軒ともゾーンの外にはみ出ていた実機報告を受けての修正)
    moods.ts              気分の定義とランダム抽選
    skills.ts              フェーズ11のスキルカタログ(BIRD_SKILL_DEFS)。各スキルは装備アイテムと同じ形のstatBonusを持つ恒久効果で、遊んでいる間の「ひらめき」で低確率に1つ獲得する
  game/
    config.ts            移動速度・気分更新間隔・治安協力金の割合・経験値カーブ・商人の来訪頻度/滞在期間/品揃え/折半率・ゲーム内時間の倍率/オフライン上限などの定数
    ai.ts                各鳥の独立AI（性格ごとの自由行動・依頼遂行(採取/討伐)・自律売買ロジック・商人との売買ロジック）。クラフト/商人納品依頼は鳥ではなくプレイヤーの操作で進むため、ここでは何もしない。「探検」「休憩」の徘徊範囲は街エリアの現在の楕円半径(AiWorld.townZoneRadius)を基準に動的に決まる。フェーズ11で「遊ぶ」(executePlay、公園・水浴び場が目的地。ひらめき抽選もここ)・「寄り道」(executeDetour、新しい行動を選び直すタイミングでのみ発生し既存の状態機械には割り込まない。実機フィードバックを受けてその場に立ち止まるだけの演出に変更済み)・「家でのお昼寝」(executeNap、休憩カテゴリの新しい選択肢)を追加。「雑談」(ambient chat)は複数の鳥を同時に見る必要があるため、ここではなくuseWorldStore.tsのtick側に実装している。stepBirdの先頭付近には、雑談中(chatPauseTicks > 0)は他の判断を一切スキップしてその場に留まらせる分岐がある(回復の次に優先度が高い)
    requests.ts           依頼を受けるかどうかのスコアリング
    combat.ts             自動戦闘の解決ロジック（貢献ダメージ比例の報酬・経験値分配、純粋関数）
    enemyAi.ts             敵の独立AI(縄張り徘徊・鳥への追跡・見失ったら引き返す。stepEnemy)。追跡は鳥の生の座標へ直進するだけで街エリアの境界を意識していなかったため、鳥が街へ逃げ込んでも敵がそのまま追ってきてしまう不具合があった——stepEnemyは現在townZoneRadiusを受け取り、街エリア内にいる鳥は追跡対象から除外する(isInsideTownZone)。倒された敵の再出現位置(respawnPosition)もここ
    recruitment.ts          残り3羽それぞれの仲間加入トリガー定義(街レベル・クエスト達成・マップでの偶然の出会い)と判定関数
    recipeUnlocks.ts        レシピ入手処理の共通関数。`maybeUnlockRandomRecipe(chance, source)`は指定確率を判定し、成功したらまだ未解放のレシピからランダムに1つ選んで解放する(採取完了時の「鳥のお土産」・依頼達成報酬・討伐報酬の3ルートで共用)。`rollMerchantRecipeOffer()`は商人の来訪ごとに未解放レシピ+価格を1件だけ提示用に選ぶ(こちらは即解放ではなく、プレイヤーが購入ボタンを押して初めて解放される)
    offlineProgress.ts      アプリを閉じていた間の「追いつき計算」(概算シミュレーション、純粋関数)。性格ごとに実測した討伐/採取のティック効率を使って、オンラインでの挙動と釣り合う量のゴールド・素材・経験値・レベルアップを算出する
    thoughts.ts            鳥をタップした時の一言セリフ(療養中・遊ぶ・寄り道も含む)。CHAT_LINESは雑談の吹き出し用の汎用セリフ集(退却時のRETREAT_LINESと同じ並び)
    birdStatus.ts          ステータスカード用の状態・目的ラベル生成(療養中の表示を含む)
    birdStats.ts            基礎ステータス+装備ボーナス+スキルボーナス(フェーズ11)を合算するgetEffectiveStats、装備品取得時に空きスロットへ自動装備するmaybeAutoEquip
    birdBaseSprites.ts      鳥本体の2頭身スプライト画像レジストリ(assets/birds/{id}/base.pngへの差し替え口。未登録時は丸型アイコン→絵文字にフォールバック)
    characterImages.ts      鳥の丸型顔アイコン画像レジストリ(assets/characters/{id}.pngへの差し替え口、将来のメニュー等向け)
    useGameClock.ts       1秒間隔のグローバルティック
  store/
    usePlayerStore.ts     永続化される所持ゴールド・素材・加工品倉庫・各店の店頭在庫（zustand + AsyncStorage、街の共有倉庫。craftItem/stockItem/restockShopItem/fulfillShopPurchase/creditMerchantTollの各アクションを持つ）。zustandのpersistは既定でトップレベルのフィールドを丸ごと保存データで上書きするだけなので、武器屋・防具屋が追加される前に保存されたセーブは`shopStock`に`weapon`/`armor`キーが無いまま復元されてしまい、それらの店を開いた瞬間にクラッシュしていた(実機報告の"Cannot convert undefined value to object")。`merge`オプションで`shopStock`だけ1段階深くマージし、保存済みの在庫は保持しつつ足りないキーは初期値で補うようにして修正した
    useWorldStore.ts      常設ワールドの状態と毎ティックのAI駆動、商人の来訪・退去ライフサイクルと売買の適用、毎ティックuseGameTimeStore.advanceOnlineを呼び出す（非永続）。討伐依頼の進捗判定は毎ティックの戦闘解決後にまとめて行う。クラフト依頼(reportCraftCompleted)・商人納品依頼(deliverToMerchant)は鳥のtick駆動ではなくプレイヤー操作から直接呼ばれる独立アクション。フェーズ11の「雑談」(ambient chat)もここのtickに実装(全鳥の最終位置を一度に見比べる必要があるため、1羽ずつしか見ないai.tsのstepBirdではなくこちら側)。雑談は「手が空いている」活動中の鳥同士のみ対象(戦闘・採掘・運搬・依頼中の鳥は対象外)で、発生確率はご機嫌度に関わらないベース値+低ご機嫌時の加算ボーナスという方式(実機フィードバックを受けた調整、CHAT_CHANCE_BASE/CHAT_CHANCE_LOW_MOOD_BONUS)。スキル獲得イベント(skillUnlockEvents)もrecipeUnlockEventsと同じ非永続キューの流儀で管理
    useTownStore.ts        永続化される街の土地の解放状況・建物・発展ポイント(developmentPoints)・街評価(reputation)・街レベルアップ演出用の履歴(levelUpEvents)（zustand + AsyncStorage。tryUnlockPlot/constructBuilding/addDevelopmentPoints/addReputationの各アクションを持つ）。constructBuildingはbuildingOptions.tsのカタログからコストを引いて区画にbuilding種別とconstructedBuildingId(どのカタログ項目を建てたか。同じ`shop`種別でも道具屋出張所と餌屋出張所を区別するために必要)を記録する。最初から解放済みの区画(リング1の東西南北4つ)はtryUnlockPlotを一度も通らない限り`plots`に一切エントリが無いままなので、constructBuildingは`get().plots[plotId]`を直接参照するのではなくTOWN_PLOT_DEFSからunlockedByDefaultを引いてensurePlotでその場に補完してから判定する(以前はこの補完が無く、それらの区画に建てようとすると課金もされず何も起きない無反応になっていた実機報告の原因)。levelUpEventsはディスクに永続化される一方、「どこまで見せたか」を数えるTownScreen側のカウンターはただのReact stateで毎回0にリセットされる仕様のため、TownScreenは自分のマウント時点でのlevelUpEvents.lengthから数え始める(既存分は「見た事にした」扱い)。そうしないと、起動のたびに過去の未読お祝いポップアップが溜まった分だけ再表示され続け、閉じきるまでマップ本体に到達できなくなる(実機で発生した実際の不具合)
    useBirdEconomyStore.ts 永続化される鳥ごとの個人ゴールド・所持素材・持ち物・装備・獲得済みスキル(フェーズ11)・仲間入り状況(isRecruited)（zustand + AsyncStorage。recruitBirdアクションで仲間入りを記録）
    useGameTimeStore.ts     永続化されるゲーム内カレンダー(gameTimeMs)とオフライン追いつき（zustand + AsyncStorage。advanceOnline/catchUpOfflineの各アクションを持つ）
    useQuestStore.ts        永続化される達成済みマイルストーンの集合(completed: Record<string, boolean>)（zustand + AsyncStorage。ハクの加入クエスト・モネの討伐マイルストーンなど、今後のクエストにも使い回せる汎用の仕組み）
    useRecipeStore.ts       永続化される入手済みレシピIDの集合(unlockedRecipeIds)のみを持つ薄いストア（zustand + AsyncStorage。isRecipeUnlocked/unlockRecipeの2アクション）。通知イベント自体(recipeUnlockEvents)はここではなくuseWorldStoreの非永続な部分に置いてある——levelUpEventsで実際に起きた「永続履歴+毎回0リセットのカウンター」不具合を再発させないための意図的な設計
  screens/
    CharacterSelectScreen.tsx 初回起動時の1羽選択画面(まだ誰も仲間になっていない間はこちらが表示される)
```

## EAS Build / Submit（iOS / App Store）

このプロトタイプは iOS 向けに EAS Build でビルドし、EAS Submit で App Store Connect に提出できる構成になっています。

### 前提条件

- Apple Developer Program のメンバーシップ
- `eas-cli` をインストールしてログイン: `npm install -g eas-cli && eas login`
- Expo アカウントでプロジェクトを初期化: `eas init`（`app.json` の `extra.eas.projectId` が自動更新されます）

### 置き換えが必要なプレースホルダー

- `app.json` → `expo.ios.bundleIdentifier`: 実際に使う Bundle ID に変更（App Store Connect で登録したものと一致させる）
- `app.json` → `expo.extra.eas.projectId`: `eas init` 実行後に自動で入る値
- `eas.json` → `submit.production.ios`:
  - `appleId`: Apple Developer アカウントのメールアドレス
  - `ascAppId`: App Store Connect 上のアプリの Apple ID（数字）
  - `appleTeamId`: Apple Developer Team ID

`eas submit` はインタラクティブに App Store Connect API キーでの認証も選択できます（`eas.json` に値を埋めずにコマンド実行時のプロンプトに従う方法でも可）。

### ビルド & 提出コマンド

```bash
# シミュレータ確認用ビルド
eas build --platform ios --profile preview

# 本番ビルド（App Store 提出用）
eas build --platform ios --profile production

# App Store Connect (TestFlight) へ提出
eas submit --platform ios --profile production --latest
```

54. **フェーズ14 修正: 拗ね→旅立ちの時間基準を、ゲーム内時間(tick)から現実の壁時計時間に変更**: item 53の「約20分で拗ね・約1時間で警告・約2時間で旅立つ」という設計が、実際にはこの秒数がticks(1tick≈1秒、かつオンライン中は`ONLINE_TIME_SCALE`で60倍速のゲーム内時間が進む)基準だったため、現実の数十秒〜数分で旅立ちまで進んでしまうという報告を受けての修正。`BirdState`/`BirdWallet`の`houselessTicks`(tickカウンタ)を`houselessSinceMs: number | null`(家がない状態が続いている、実時刻ベースのepoch msタイムスタンプ。家がある間はnull)に置き換え、`useWorldStore`のtickでは`Date.now() - houselessSinceMs`という単純な経過時間の比較でしきい値判定するように変更した(`HOUSELESS_SULK_MS`=24時間、`HOUSELESS_WARNING_MS`=36時間、`HOUSELESS_LEAVE_MS`=48時間——24時間・48時間は依頼で明示された数値、36時間は「旅立つ瞬間ではなく実際に行動できる猶予を残した警告」にするための中間地点として今回選んだ値)。この方式の最大の利点は、**アプリが閉じている間の経過時間もそのまま判定に使える**こと(`Date.now()`との単純な差分なので、オフライン進行の近似シミュレーション(`game/offlineProgress.ts`)のような特別な対応が一切不要——真夜中に一度だけ開いたセッションでも、閉じていた間の経過時間を含めて正しく判定される)。ただしtick間の差分(前のtickの値としきい値を比較)で「ちょうど今しきい値を超えた瞬間」を検知していた旧方式が使えなくなった(実時刻は複数tickをまたいで一気に進みうるため)ので、代わりに`houselessSulkLogged`/`houselessWarningShown`という「このエピソードで既に表示したか」を示す一度きりフラグ2つを追加し、しきい値を超えている間ずっと同じログ・警告が毎tick再発火し続けるのを防いだ(旅立ち自体は`isRecruited`をfalseにする副作用そのものが自然な一度きりガードになるため、専用フラグは不要)。プレゼントを渡した際のリセットも、`houselessSinceMs`をnullに戻す(+両フラグもfalseに戻す)ことで「基準時刻からやり直す」形にそのまま対応。既存の見た目(拗ね演出・`HouseWarningModal`・`HouseDepartureModal`・`GiftBirdModal`)は変更なし。連続tick・単発tick(長いオフライン明けの1回だけの再開を想定)・プレゼントによるリセット後の再発火、それぞれのシナリオを軽量シミュレーションスクリプトで確認し、`npx tsc --noEmit`・`npx expo export --platform ios`とも確認済み。
